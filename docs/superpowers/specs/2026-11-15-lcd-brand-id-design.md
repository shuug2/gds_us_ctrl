# LCD 브랜드 번호 — V31 단일 바이너리 설계

> **문서 요약**: V31 보드부터 컨트롤러 펌웨어를 업체별로 따로 빌드하지 않고 **바이너리 하나**로 관리한다. 업체(브랜드)는 업체별 DGUS LCD 세트의 `22_Config.bin` 빈 VP 한 칸에 담긴 **브랜드 번호**로 정하고, 펌웨어가 부팅 때 그 칸을 읽어 LCD 모델명 규칙을 고른다. 번호 0(옛 세트)·읽기 실패·모르는 번호 = gdsonic. V30 은 지금처럼 컴파일 타임 BRAND 그대로. 목적 = 보관본·빌드 산출물 관리 부담 감소(V31 `.bin` 4개 → 1개), 부수 효과 = 출하 업체 전환이 LCD SD 세트 교체만으로 끝난다. (2026-11-15 사용자 결정)

---

## 1. 의도

- **왜**: 관리 부담. 브랜드가 바꾸는 것은 LCD 모델명 문자열 하나뿐(`app_lcd_send_model_str`, `fw/src/app_lcd.c`)인데, 이것 때문에 HW 리비전 × 브랜드만큼 `.bin`·SHA·보관 폴더 줄·Flasher 슬롯·downloader 선택지가 늘어난다.
- **성공**: V31 은 `.bin` 하나로 4업체 출하. 업체 전환 = 해당 업체 LCD 세트 SD 로 넣고 전원 재투입 → 로고·모델명이 그 업체 것으로 나온다.

## 2. 목표 / 비목표 / 실패 조건

- 목표: V31 에서 브랜드를 LCD 세트가 정한다. 모델명 문자열은 지금 업체별 빌드와 **글자 단위로 같다**.
- 비목표: V30 변경(컴파일 타임 BRAND 유지 — 사용자 결정 "V31 이상만"). 펌웨어의 다른 동작을 브랜드로 가르기. Modbus 에 브랜드 노출.
- 실패 조건(동작해도 실패): ① 같은 업체·주파수·타입에서 모델명이 지금 빌드와 다르다 ② LCD 세트가 없거나 늦게 떠서 컨트롤러 부팅·운전이 지연·멈춘다 ③ 옛 세트(번호 칸 없음)에서 모델명이 비거나 깨진다.

## 3. 제약

- `22_Config.bin` = DGUS II 변수 영역 초기값(128 KB = VP 0x0000~0xFFFF, 워드당 2바이트, 빅엔디언으로 추정 — **실기 확인 필요**). 세트 3종에 있음(gdsonic = dongin 동일 SHA, moohan 다름).
- 펌웨어에 읽기 경로 있음: `dgus_read_word(addr, &val, timeout)` (`fw/drivers/dgus_lcd.c:282`, 블로킹 + 타임아웃). 부팅 때 `SYS_PIC_NOW` 읽기에 이미 쓴다(`app_lcd.c:257`). 단 주소를 8비트로 잘라 보낸다 → VP 0x00xx 만 읽힌다(§6.2).
- 펌웨어가 쓰는 VP = 0x1000~0x1490 구간(`fw/include/*.h`). 브랜드 칸은 펌웨어도 DGUS 화면 위젯도 쓰지 않는 VP 여야 한다.
- LCD 세트 생성 = `hw/lcd/tools/lcdset.py` + `brands.json`(업체마다 `fw_brand` 칸 이미 있음). **이 툴은 lcd 세션 담당** — 변경은 그쪽과 합의.
- downloader 입력 계약 = ctrl `releases/` 형식(허브 `gdsonic/CLAUDE.md` §4.3). 파일명 변경은 downloader 와 **상의** 대상.
- FLASH 51.8% 사용 — 브랜드 규칙 5개를 다 넣어도 여유 충분.

## 4. 접근

| 안 | 내용 | 판단 |
|---|---|---|
| **A. `22_Config.bin` 빈 VP 에 브랜드 번호** | lcdset 이 세트 생성 때 기록, 펌웨어 부팅 때 1회 읽기 | **채택** — 이미 업체별로 관리하는 세트에 2바이트 추가, SHA 계약 유지 |
| B. DGUS 내장 플래시 DB | downloader 가 LCD UART 로 따로 기록 | 기각 — 세트 파일에 안 보여 추적 불가, 출하 단계 추가 |
| C. 모델명 문자열 18조합을 LCD 에 | 펌웨어는 번호로 가리키기만 | 기각 — 규칙이 LCD 툴로 옮겨가 관리처가 늘어남 |
| (원안) downloader 가 `.bin` 의 모델명을 패치 | | 기각 — 브랜드마다 문자열 **생성 규칙**이 달라 자리 치환 불가, 패치하면 SHA 대조 계약이 깨짐 |

## 5. 결정된 설계 (사용자)

- 방식 = A.
- **번호 0 = gdsonic.** (옛 세트 호환)
- **HW V31 이상에만 적용.** V30 은 현행 그대로.
- **선행 게이트 = 실기 시험**: 패널이 부팅 때 `22_Config.bin` 을 VP 로 실제 로드하는지 아직 근거 없음(T5L 은 CFG 설정으로 22 로드가 꺼져 있을 수 있음). 첫 작업으로 gdsonic 세트 빈 VP 에 시험값을 넣어 SD 로 올리고 펌웨어에서 읽는다. **실패하면 이 설계는 접고 업체별 `.bin` 을 유지한다**(T5LCFG 내려받기 = 2025 배치 터치 사망 함정이라 시도하지 않음, B안 부활 없음).
- **역할 분담**: ctrl = 펌웨어 + 계약(브랜드 VP 주소·번호표). lcd 세션 = 세트에 번호 기록(`lcdset.py`·`brands.json`·기준 세트 moohan) + `22_Config.bin` 동일성 검사 예외. gdsonic 세트는 번호 0 = gdsonic 이라 수정 불요.
- **재읽기**: 부팅 때 1회 + **패널이 나중에 뜰 때**(`handle_sys_pic_now`, `fw/src/app_lcd_input.c:433-447` — 모델명 재전송하는 그 자리)에 한 번 더 읽는다.

## 6. 설계 상세 (제안 — 빌더가 확정할 칸은 §7)

### 6.1 브랜드 번호표 (정본 = `fw/include/app_brand.h`, lcdset `brands.json` 은 같은 숫자)

| 번호 | 브랜드 |
|---|---|
| 0 | (미설정) → GDSONIC |
| 1 | GDSONIC |
| 2 | MOOHAN |
| 3 | DIAMT |
| 4 | POWERTECH |
| 5 | MAKETECH |

모르는 번호(6 이상) → GDSONIC. 새 업체(SAMA·SONOSYS)는 번호 추가 + 규칙 추가 = 펌웨어 새 버전 1회. 예약(제안): 6 = SAMA, 7 = SONOSYS — 둘 다 white 계열 세트 build 완료(2026-11-15), 모델명 규칙 미정이라 펌웨어 규칙은 정해진 뒤.

### 6.1b 브랜드 VP (lcd 세션 조사 2026-11-15 기준 제안)

- **VP 0x1500** (내 판단 — lcd 세션 권고 후보 중 하나). 근거: 화면 위젯(14ShowFile)이 쓰는 VP = 0x1000~0x1497, 펌웨어 최대 = 0x1495, 22_Config 초기값 구간도 0x1495 까지 → 0x1498 이상은 세 쪽 모두 미사용. 0x0000~0x0FFF 는 T5L 시스템 영역이라 제외.
- `22_Config.bin` 오프셋 = VP×2 (lcd 실측: VP 0x1000 → 파일 0x2000 에 모델명 "GD-35M…" 초기값). 엔디언은 게이트 시험에서 확인.
- 22_Config 에 모델명 초기값이 이미 들어 있다는 사실은 패널이 22 를 로드한다는 정황이지만, 펌웨어가 부팅 때 덮어쓰므로 증거는 아니다 — 게이트 시험은 그대로 필요.

### 6.2 펌웨어

- V31 빌드는 `BRAND` 축을 쓰지 않는다 — 5개 규칙을 모두 넣고 런타임 번호로 고른다. V30 빌드는 지금 `#ifdef` 그대로.
- 모델명 함수는 브랜드별 규칙을 함수 하나씩으로 나누고(현 `#ifdef` 블록 내용 그대로 이동), V30 은 컴파일 타임 상수로, V31 은 부팅 때 읽은 번호로 그중 하나를 부른다 — 규칙 코드는 한 벌.
- 읽기 시점 = ① 부팅: LCD 초기화 직후, 첫 `app_lcd_send_model_str` 전 ② 패널 재기동: `handle_sys_pic_now` 에서 모델명 재전송 직전. 짧은 블로킹(수십 ms) — 그 순간은 패널이 막 뜬 때라 운전 중이 아니다. 재시도 몇 회(기존 `DGUS_PAGE_CONFIRM_RETRIES` 패턴) 후 실패면 GDSONIC. 결과는 RAM 에만(FRAM 저장 안 함 — 세트가 정본).
- `dgus_read_word` 는 지금 주소를 8비트로 잘라 보낸다(`fw/drivers/dgus_lcd.c:293` → `dgus_read_var((uint8_t)addr)`). 브랜드 VP 가 0x0100 이상이면 16비트 주소로 넓힌다(기존 SYS_PIC_NOW 호출 거동 불변). (빌더 확인 사항, 내 판단)
- 순수 함수(번호 → 브랜드, 브랜드·freq·type → 문자열)는 host 테스트: 5브랜드 × 6주파수 × 3타입 = 90조합이 현 업체별 빌드 출력과 같음을 확인.

### 6.3 LCD 세트 (lcd 세션 담당 — ctrl 은 계약만 건넨다)

- ctrl 이 건넬 계약 = 브랜드 VP 주소 + §6.1 번호표 + 오프셋·엔디언(게이트 시험 결과).
- lcd 세션 몫: `brands.json` 업체마다 `brand_id`, `lcdset.py` 가 세트 생성 때 `22_Config.bin` 브랜드 VP 에 2바이트 기록. 기준 세트 moohan(DGUS 툴 편집 대상, build 대상 아님)에 번호 2 넣는 경로와, DGUS 툴 재내보내기 때 그 칸이 보존되는지 확인. `22_Config.bin` 기준-파생 바이트 동일성 검사(`lcdset.py:35,114-116`)에 브랜드 워드 예외.
- gdsonic 세트 = 번호 0 그대로(수정 불요). 같은 family 라도 이제 `22_Config.bin` 은 업체마다 다를 수 있다.
- 벤치(§8)는 lcd 세션 산출물이 나와야 가능 — 계획의 의존으로 둔다.

### 6.4 보관본·양산 (downloader 상의)

- V31 파일명 제안 = **`gds_us_ctrl_hw31_v<버전>.bin`**(브랜드 없음). V30 은 현행 `gds_us_ctrl_<brand>_v<버전>.bin`.
- 다음 보관본 = V30 4개 + V31 1개 = `.bin` 5개(이전 결정 8개 대체).
- Flasher 슬롯 1 = 이 V31 `.bin`. 출하 업체 전환 = **해당 업체 LCD 세트 SD 만**(UART 재다운로드 불필요). 버전 README·`production/README.md`·허브 §4.3·§4.5 갱신.
- 이 설계가 같은 날 `production/README.md` "다음 보관본부터 — V31 생산·출하 흐름" 절(업체별 `_hw31` 을 UART 로 재다운로드)을 **대체**한다(내 판단 — 게이트 PASS 시). `models.txt`·`mkproduction.sh` 구조 변경과 downloader 상의는 다음 보관본 작업 때.

## 7. 빌더에게 남긴 것

- 브랜드 VP 0x1500(§6.1b) 의 엔디언 실기 확인.
- 읽기 재시도 횟수·타임아웃(부팅 지연 상한 안에서).
- CMake/`fw.sh` 에서 V31 일 때 BRAND 처리(무시 또는 오류)와 빌드 폴더 이름.

## 8. 검증

- 0단계(게이트): `22_Config.bin` 시험값 → 펌웨어 읽기 일치. FAIL = 중단(§5).
- host: §6.2 90조합 동일성.
- 벤치(V31): 세트 4종 각각 SD → 모델명·로고 확인 / 번호 칸 없는 옛 세트 → GDSONIC 모델명 / LCD 분리 부팅 → 컨트롤러 정상 기동 + GDSONIC / LCD 를 늦게 연결(부팅 4 s 대기 뒤) → 패널이 뜨면 그 업체 모델명.
