# 원격 hold-to-run — `gds_us_ctrl` 에 대한 요구사항

> **문서 요약**: 원격기(`gds_us_remote`)의 START 를 **컨트롤러 RUN 버튼과 같은 모멘터리
> 방식(누르는 동안 가동, 떼면 정지)** 으로 만들기로 했다(2026-09-05 사용자). 원격기만
> 고치는 안은 기각됐다 — 통신이 끊기면 원격기는 정지를 보낼 수 없고 런은 30초 상한까지
> 돈다(E-10). 그래서 **컨트롤러에 "원격 hold 런의 유지 신호가 끊기면 정지"(hold 워치독)** 를
> 요구하고, 그것이 선 뒤에 원격기에 hold-to-run 을 붙인다. 이 문서는 hold-to-run
> 기능 동등성을 위해 컨트롤러가 갖춰야 할 것의 **전수 목록**이다 — 필요한 것 6건
> (R-4 판별자 · R-1 hold 워치독 · R-2 런 구분 · R-3 유지 신호 · R-6 기존 정지 경로 승계 ·
> R-11 게이트 닫힘 시 정지), 권장 1건(R-5 정지 사유 관측), **불필요로 판정한 것 3건**
> (R-7 혼 하강 · R-8 양손 abort · R-9 `EN_SAFTY`)과 그 이유, 소스를 읽다 발견한 것
> 5건(R-10)을 담는다. 🔴 **2026-08-02 안전 스펙 §3 "진행 런을 중단하지 않는다" 와
> 정면으로 부딪히는 요청**이라 그 논증을 R-1 안에 뒀다 — 결론은 "다른 사안이다,
> 단 hold 런에 한정할 때만" 이다.
>
> 🔴 **구현 방법은 이 문서가 정하지 않는다.** 레지스터 번호·값 인코딩·FSM 배치·
> 타임아웃 확정값은 **이 저장소가 정한다.** 기존 관행 그대로다: *"소비 측 관점의
> 제안 정본이고, 펌웨어 구현 정본은 그쪽 설계 spec 이다 — 갈리면 실코드를 가진 쪽이
> 이긴다."*

🔴 **용어**: 이 문서의 "워치독"은 전부 **hold 워치독**(유지 신호 소실 → 런 정지)이다.
컨트롤러의 **IWDG**(MCU 하드웨어 워치독, 실측 T=4.45s, 펌웨어 hang 대비)와 **완전히
다른 물건**이다 — 두 저장소 문서에서 "워치독" 한 단어가 다른 것을 가리키면 사고가
난다(2026-09-06 컨트롤러 세션 제안, 수용).

**요청자**: `gds_us_remote` (`~/dev/work/gds_us_remote`)
**작성**: 2026-09-05
**선행 문서**: `2026-08-30-remote-parity-requirements.md`(형식 정본) ·
원격기 `docs/superpowers/specs/2026-08-02-remote-enable-safety.md` §3(충돌 지점) ·
원격기 `CLAUDE.md` §6·§7

## 0. 왜 이 요청이 생겼나

**컨트롤러의 START 는 원래 모멘터리다.** 물리 버튼 `B_START(PA15)` 는 "모멘터리
hold-to-run" 으로 press 엣지에 START, release 엣지에 RUN_RELEASE 를 낸다
(`fw/src/app_input_fsm.c:33-37`, `fw/src/app_input.c:96-97`). LCD RUN 버튼도 같다 —
press=START / release=RUN_RELEASE (`fw/src/app_lcd_input.c:215-244`, V30 data=0
토글 재구성 포함). 반면 **원격기의 START 는 탭 1회 = 정지 명령이 올 때까지 가동**이다.
"컨트롤러와 같이" 만들려면 원격기가 release 에 STOP 을 보내면 되지만, 그것만으로는
**통신이 끊긴 순간 손을 떼도 기계가 안 선다** — `US_COMM` 런은 링크가 끊겨도 계속
돌고 정지 경로는 30초 절대 상한·HAND on-time 상한·energy 종료·STOP 명령뿐이다
(`fw/src/app_reg.c:400-417, 421-460`; 원격기 안전 스펙 E-10).

즉 hold-to-run 의 약속("놓으면 선다")을 원격기 혼자서는 지킬 수 없다. 약속을 지키는
쪽은 **런을 돌리고 있는 컨트롤러**여야 한다.

| 층 | 원격기가 할 수 있는 것 | 컨트롤러만 할 수 있는 것 |
|---|---|---|
| 정상 경로 | release 즉시 STOP 전송 (오늘 실측 확정 36ms) | — |
| 링크 단절·원격기 정지 | **아무것도 못 한다** | **유지 신호 소실 → 정지** |
| 구펌웨어 판별 | 판별자가 있어야 한다 | 판별자 제공 |

## 1. 요구 전수 목록 (우선순위 순)

각 항목은 **필요/불필요 · 근거 · 없으면 무슨 일이 생기나** 를 갖춘다.

### R-4 — capability 판별자 ★ 필수 (가장 먼저)

**무엇**: 원격기가 FC03 폴링 프레임 안에서 **"이 펌웨어에 hold 워치독이 있다"** 를
**구펌웨어 전부(F-A 펌웨어 `e5ea557` 포함)와 구분해** 읽을 수 있어야 한다.

**왜 이번엔 다른가** — 지난번(`bit7/bit8`, 2026-09-05) 에 판별자를 안 둔 결정은
합리적이었다: 비트가 없어도 원격기의 **fallback(시간 기반 hold)이 이미 안전**했고,
대가는 표시 품질(탭 직후 60ms 둘 다 점등, hold 를 못 줄임)뿐이었다. 그 대가는
원격기가 `absence_is_evidence` 를 만들어 흡수했다(`components/gds_controller/src/command.c:92-104`).

이번엔 **안전한 fallback 이 없다.** 판별자가 없으면 원격기는 둘 중 하나다:
- (a) hold-to-run 을 **켜지 않는다** → 기능이 죽는다. 요청의 목적 소멸.
- (b) **믿고 켠다** → 구펌웨어에 붙으면 조작자는 "놓으면 선다" 고 배운 채로 실제로는
  30초까지 도는 기계 앞에 선다. **거짓 안전을 파는 것**이다.

(a)와 (b) 사이에 "0 을 모름으로 취급" 같은 중간 지대가 **없다** — 워치독은 관측이
아니라 **거동**이라, 원격기가 보수적으로 해석할 값 자체가 없다.

**레지스터 여유 선점 회피라는 지난 근거는 그대로 존중한다.** 레지스터를 **한 칸도
안 먹는** 방법이 최소 둘 있고, 셋째는 이미 소비된 칸이다 — 선택은 이 저장소가 한다:
1. **기존 매직의 버전 바이트 승격** — `0x31 CFG_CAP = 0xFA01` 의 하위 바이트가
   `0x2A REMOTE_CAP = 0x5201` 과 같은 설계 의도("하위 바이트 = 프로토콜 버전", 원격기
   안전 스펙 §4.1)를 갖는다면 `0xFA02` = "F-A v2: hold 워치독 포함" 이 된다.
   ⚠️ 원격기 현행 판정은 **정확 일치**다(`components/gds_controller/src/snapshot.c:122`
   `regs[0x31] == 0xFA01`) — 원격기는 hold 작업과 함께 `상위 0xFA && 하위 >= N` 으로
   고친다. **`gds_us_hmi` 는 통보가 필요하다**(그쪽 HANDOFF 에 이미 STATUS 확장
   통보 미실시가 열려 있다).
2. **STATUS 예비 비트** — `0x200~0x8000` 7비트가 남아 있다(`fw/include/app_modbus_core.h`
   STATUS 블록). "capability 를 STATUS 에" 는 의미론이 어색하지만 프레임 원자성은
   가장 좋다.
3. **결번 `0x2C`** — 이미 소비된 칸이고 REMOTE 빌드에서 0 미러다
   (`fw/src/app_modbus.c:278`). ⚠️ STD 빌드는 미러가 없어 잔류값이 남으므로
   (`app_modbus.c:273 #if defined(MODEL_REMOTE)`) 이 칸을 쓰려면 **모델 무관 미러**로
   바꿔야 한다 — 그러지 않으면 `0x31` 이 `0x2A` 로 F-A 를 오판하던 것과 같은 함정이
   재현된다.

⚠️ 이 저장소의 진행 비트 주석이 이미 이 문을 열어 뒀다: *"상태 기반 hold 가 필요해지면
그때 capability 를 신설한다"* (`fw/include/app_modbus_core.h` `MB_STATUS_SEEK` 위 주석).
**워치독은 정확히 "상태 기반 hold"다.**

**없으면**: 원격기는 (a)를 택할 수밖에 없다 — 이 문서의 나머지 항목을 전부 구현해도
원격기에서 hold-to-run 을 켤 수 없다. 이 항목이 **1번**인 이유다.

### R-1 — 유지 신호 소실 시 정지 (hold 워치독) ★ 필수

**무엇**: 컨트롤러가 **hold 방식으로 시작된 원격 런**(R-2)에 대해, 원격기의
**유지 신호**(R-3)가 **T 시간** 안에 오지 않으면 그 런을 **정지**시킨다.
정지는 STOP 명령(`US_CMD_RUN_RELEASE`)과 **같은 결과**여야 한다 — 피크 래치·IDLE
복귀·STATUS `US` 0 (`fw/src/app_reg.c:210-243`).

#### 2026-08-02 안전 스펙 §3 과의 충돌 — 정면으로

§3 "가동 중 해제 거동" 행은 **명시적으로** "해제(만료·침묵·LCD 수동)는 신규 명령·쓰기만
차단하고 진행 중인 런은 중단하지 않는다" 고 정했고 근거 셋을 댔다: ① 급정지가 새
위험(사이클 중단·혼 하강 상태 방치·작업물 파손) ② 링크 단절 시 현행 거동과 일관
③ 30초 상한이 backstop. 이 요청은 "신호가 끊기면 런을 세워라" 다. **반대다.**

같은 사안인지 따져 봤다. 결론은 **다른 사안이다 — 단 R-2 로 hold 런에 한정할 때만.**

| | §3 의 게이트 해제 | hold 런의 유지 신호 소실 |
|---|---|---|
| 런의 근거 | 조작자가 "가동 시작" 을 **완결된 명령**으로 냈다. 런은 정지 명령·상한까지 도는 것이 **약속**이다 | 조작자의 **지속적 동의(누르고 있음)** 가 그 런의 **유일한 근거**다. 런은 "누르는 동안" 이 약속이다 |
| 소멸한 것 | **부수 조건**(허가 창·링크 활동)이 소멸했다. 런 자체의 약속은 살아 있다 | **기동 근거 자체**가 소멸했다(동의 철회 또는 그것을 확인할 수 없음). 세우는 것이 약속의 이행이다 |
| 세우면 | 조작자가 내린 결정을 시스템이 **뒤집는다** | 조작자가 내린 결정을 시스템이 **집행한다** |
| §3 근거 ① 혼 하강 | 성립 가능(weld 사이클 US_CYCLE 도 대상) | **성립하지 않는다** — R-7 참조(원격 런은 실린더를 안 움직인다) |
| §3 근거 ① 작업물 파손 | 정지가 의외의 시점 | 조작자가 손을 뗀 것과 **같은 결과**다 — 패널 RUN 버튼을 떼면 원래 그렇다 |
| §3 근거 ②③ | "계속 도는 것이 **허용 가능**하다" 의 근거 | "세울 **필요가 없다**" 의 근거였지 "세우면 안 된다" 가 아니다 |

한 가지 더 — **이 저장소가 이미 같은 판단을 내린 곳이 있다.** LCD RUN 버튼의
lost-release(페이지 이탈·패널 리셋로 release 엣지가 영영 안 오는 경우)를 이 저장소는
"30초 상한이 커버하는 **리스크**" 로 분류하고 `swallow_start`·`run_key_reanchor` 로
방어해 왔다(`fw/src/app_lcd_input.c:165-182,222-239`, `fw/src/app_reg.c:425-428`
"V30 lost-release 리스크"). 즉 **"쥐고 있던 런이 쥠이 끝난 뒤에도 도는 것"을
이 저장소는 원래 결함으로 본다** — 더 나은 신호가 없어서 참아 온 것이다. 워치독은
그 결함에 대한 신호를 원격 경로에 한해 만드는 것이다.

🔴 **논증이 성립하는 조건**: hold 워치독이 **hold 런에만** 걸려야 한다. 탭 START(기존
`US_COMM` 런)에까지 걸면 §3.1 을 실제로 뒤집는 것이고, 그때는 §3 근거 ②(링크 단절 시
런 지속)도 함께 깨진다. 그래서 R-2 가 R-1 의 필수 짝이다.

🔴 **2026-09-06 정정 — "예외"가 아니라 "적용 범위 밖"이다**(컨트롤러 세션 지적, 수용).
구판은 "§3 표에 hold 런은 예외라고 개정으로 명기하라"고 요구했으나 **철회한다.**
`2026-08-02-remote-enable-gate-decision.md:49` 의 주어는 **「가동 중 *해제*」라는
사건**이지 "런이 죽는 모든 경우"가 아니다. 그 런은 기동 근거가 살아 있고 **권한만**
사라진 런이고, hold 런은 기동 근거가 매 순간 갱신되는 **새 범주**라 2026-08-02 시점에
판단 대상이 아니었다. → **§3.1 은 한 글자도 고치지 않는다.**
⚠️ **"예외"로 적으면 다음 사람이 §3.1 을 일반 원칙으로 읽고 되살린다.**

⚠️ **위 표의 "§3 근거 ①" 인용은 우리 저장소의 확장 서술이었다.** 컨트롤러 정본
(`:49`)은 *"소프트웨어 판단에 의한 급정지가 오히려 더 위험할 수 **있고**, 30초 절대
상한이 backstop"* 두 줄이 전부이고 하나는 약한 형태다. "혼 하강 상태 방치"·"작업물
파손"은 원격기 `2026-08-02-remote-enable-safety.md:152` 가 덧붙인 것이다. 따라서
**R-7 의 반증은 유효하지만 §3.1 의 기둥을 무너뜨린 것이 아니다 — 애초에 기둥이
아니었다.**

**없으면**: 원격기 hold-to-run 은 정상 경로에서만 약속을 지키고 단절 시 30초까지 돈다
— 사용자가 기각한 "원격기만 먼저" 안과 같다.

### R-2 — hold 런과 일반 원격 런의 구분 ★ 필수

**무엇**: 컨트롤러가 **"이 런은 hold 방식으로 시작됐다"** 를 알아야 한다. 따라서
원격기가 **hold 시작을 일반 START 와 구분해 요청할 수단**이 필요하다.

**왜**: R-1 논증의 성립 조건이다. 워치독을 모든 `US_COMM` 런에 걸면 ① §3 를 뒤집고
② `gds_us_hmi`·`mbpoll` 같은 **다른 마스터의 탭 START 가 폴링을 멈추는 순간 서기
시작**한다 — 그쪽은 유지 신호를 모른다.

🔴 **구펌웨어 fail-safe 요구**: hold 시작 요청은 **구펌웨어에서 기동으로 해석되면 안
된다.** 판별자(R-4)가 원격기의 *표시*를 정직하게 만든다면, 이 요구는 원격기가
판별을 **틀렸을 때** 물리 안전을 지킨다 — 워치독 없는 펌웨어에서 hold 런이 시작되는
경로를 구조적으로 막는다. 두 겹은 다른 고장을 막는다.
참고 사실(활용 여부는 그쪽 판단): 현행 apply 체인은 `holding[START] == 1u` 일 때만
디스패치한다(`fw/src/app_modbus.c:363`) — 값 1 이외의 START 쓰기는 오늘 펌웨어에서
기동되지 않는다.

**없으면**: 워치독의 적용 범위를 정할 수 없어 R-1 이 §3 위반이 되거나, 다른 마스터가
피해를 본다.

### R-3 — 유지 신호의 성격 ★ 필수

**무엇**: 원격기가 **누르고 있는 동안만** 주기적으로 보내는, 컨트롤러가 hold 런과
결부할 수 있는 신호. 성질 5개:
1. **읽기(폴링)와 구분된다.** 🔴 기존 `s_remote_ms` 로는 안 된다 — 유효 디코드
   전부에 찍히고 읽기도 포함이라(`fw/src/app_modbus.c:102-106, 741`,
   `fw/src/app_modbus_tcp.c:192`; `app_remote_en_fsm.c:56-58` "읽기도 생존 신호")
   조작자가 손을 떼도 폴링이 계속 돌아 신호가 끊기지 않는다. 폴링은 **원격기의
   생존**을 나르고, 유지 신호는 **조작자의 의도**를 날라야 한다.
2. **기동 권한이 없다.** 유지 신호는 **도는 hold 런을 연장할 뿐**, IDLE 에서 도착해도
   기동하지 않는다. 🔴 이것이 없으면 E-STOP 해제·30초 상한·패널 정지 직후에 도착한
   늦은 유지 신호가 **기계를 다시 돌린다.**
3. **영속되지 않는다.** cfg 필드·FRAM 을 거치면 안 된다 — 초당 수 회 도착한다.
   명령 레지스터처럼 소비되는 성격이어야 한다.
4. **다른 FC06 과 섞여도 유실되지 않는다.** TCP 는 poll 당 write-apply 1건이고 잔여는
   다음 tick 으로 이월된다(`fw/src/app_modbus_tcp.c:161-210`). 유지 신호 하나가 파라미터
   쓰기 뒤로 한 tick 밀리는 것은 T 안에서 흡수돼야 한다(§2).
5. **원격기 부담이 작다.** 원격기는 초당 폴 16~19회 + 유지 신호 <=10회를 한 소켓으로
   보낸다. 왕복 하나가 15~18ms 라 여유는 있다.

**없으면**: 워치독의 입력이 없다. `s_remote_ms` 를 쓰면 손을 떼도 절대 안 선다 —
워치독이 있어도 hold-to-run 이 아니다.

### R-5 — 정지 사유 관측 (권장)

**무엇**: 원격기가 **마지막 정지의 사유**를 구분할 수 있으면 좋다 — 최소 {STOP 명령 ·
30초 상한 · 워치독 · 그 외(E-STOP/패널/energy)}.

**왜**: hold 중 기계가 서면 조작자는 아직 누르고 있다. 화면이 "왜 섰는지" 를 말해야
하는데 지금 컨트롤러는 어떤 정지도 사유를 남기지 않는다 — `reg_stop_run` 은 래치와
IDLE 뿐이고(`fw/src/app_reg.c:99-113`) mon 조차 `REG_TRACE` 빌드에서만 찍는다
(`:414-416`). 특히 **워치독 정지는 원격기 자신의 고장 신호**(유지 신호를 못 보냈다)라
"기계가 섰다" 와 다른 조치를 요구한다.

**권장이지 필수가 아닌 이유**: 원격기가 근사 추론할 수 있다 — 자기 시계로 30초 도달
여부, 자기 전송 결과로 유지 신호 실패 여부, `STATUS bit1` 로 E-STOP. 다만 그 추론은
**관측이 아니라 추정**이라 원격기는 "30초 상한 도달로 정지 **(추정)**" 처럼 양상을
붙여 말할 것이다. 이 저장소가 진행 비트를 신설해 준 것과 같은 이유(추정을 관측으로)로
값이 있지만, 레지스터 여유(7칸)를 쓰는 결정이라 그쪽 판단에 맡긴다.
⚠️ 이것은 hold 전용이 아니다 — 오늘 탭 START 도 30초 상한 정지와 패널 STOP 이 화면에서
구분되지 않는다.

**"hold 런 진행 중" 비트**는 **요청하지 않는다** — 원격기는 자기 hold 세션을 안다.
다른 마스터의 hold 런을 표시할 필요는 없다.

**없으면**: 원격기가 "장치에서 정지됨 · 사유 미확인 / 30초 상한 (추정)" 으로 표시한다.
기능은 된다, 문구가 덜 정직할 뿐이다.

#### 2026-09-06 판정 — **권장 유지**(필수로 올리지 않는다)

컨트롤러 세션이 승격 근거를 제시했다: *hold 워치독이 원격기의 release 유실 버그를
backstop 으로 덮어 "가끔 안 선다"를 "T 만큼 늦게 선다"로 바꾸고, 그러면 그 버그를
실기에서 못 잡는다.* **차폐 우려 자체는 옳고 이 프로젝트의 반복 실패 유형**이다
(하네스·backstop 이 거짓 안심을 준다 — HANDOFF §4).

🔴 **그러나 차폐 층의 위치가 하나 바깥이다.** 원격기 설계에는 이미 **증거 타이머**가
있다: `LV_EVENT_PRESSING`(indev 읽기마다, 약 15ms)이 약 100ms 끊기면 **release 로
확정하고 STOP 을 보낸다.** LVGL 이 `DISABLED` 객체에 `RELEASED` 를 안 보내는
문제(`lv_indev.c:1345-1350`)는 손가락이 떨어지면 `PRESSING` 도 함께 멎으므로 **T(약
500ms)에 한참 못 미쳐 우리 쪽에서 잡힌다.** 즉 **첫 차폐 층은 hold 워치독이 아니라
우리 자신의 fallback** 이고, 검출기도 거기 있어야 한다.

→ **검출은 원격기가 맡는다(우리 쪽 필수 요구로 승격)**: release 의 **출처**를 로그에
남긴다 — `RELEASED` 이벤트 / `PRESS_LOST` / **증거 타임아웃** / 화면 이탈 넷을
구분한다. **증거 타임아웃이 상시 출처가 되면 LVGL 배선이 깨진 것**이고, 그 신호는
컨트롤러 레지스터 없이 우리 로그만으로 선다. 결함에 더 가깝고 더 싸다.

**그래도 R-5 가 유일하게 덮는 잔여가 있다**: 우리 release 검출과 STOP 전송이 **둘 다**
실패한 경우(comm 태스크 정체·링크 단절) — 그때는 워치독이 세운 것과 "우리 STOP 이
먹었는데 ack 를 못 봤다"를 구분할 수 없다. **다만 이것은 안전 공백이 아니라 링크 품질
진단 공백**이라 승격 근거로는 약하다. 레지스터 1칸의 값은 그쪽이 판단할 몫이다.

### R-6 — 기존 정지 경로 승계 ★ 필수

**무엇**: hold 런도 **기존 `US_COMM` 런과 동일하게** ① 30초 절대 상한 ② E-STOP 매 tick
강제 정지 ③ energy 모드 종료/OVTIME ④ HAND on-time 상한 ⑤ STOP 명령 ⑥ 패널 RUN
release(대칭 정지) 의 대상이어야 한다. 워치독은 **추가** 경로이지 대체가 아니다.

**왜 굳이 적는가**: 🔴 이 세 경로는 전부 **`us_run_status` 소스 값의 열거**로 판정한다 —
`fw/src/app_reg.c:410-411`(30초, TOUCH/COMM/REMOTE/CYCLE) · `:433-434`(energy) ·
`:452`(HAND on-time, COMM/REMOTE). hold 런을 **새 소스 값**으로 표현하기로 결정한다면
그 값이 세 목록에서 빠지는 순간 **hold 런이 30초 상한을 벗어난다.** 유지 신호가
계속 오는 한 무한히 돈다. 방법을 정하지 않는 문서지만 이 함정은 방법과 무관하게
알려야 했다.

**없으면**: 최악의 경우 hold 런이 유일하게 30초 상한이 없는 런이 된다.

### R-11 — 게이트 닫힘 시 hold 런 정지 (필수 · 방법 협의)

**무엇**: hold 런 도중 원격 활성화 게이트가 닫히면(스위치 OFF·E-STOP) 그 hold 런은
**T 안에 서야 한다.**

**왜**: hold 런의 근거는 "원격 조작자의 지속 동의 **그리고** 기계 쪽 허용" 이다.
기계 쪽 사람이 스위치를 내리는 것은 허용의 철회다. §3 는 게이트 해제가 런을 안 세운다고
했지만 R-1 의 논증이 여기에도 그대로 적용된다 — hold 런에 한해서.
E-STOP 은 이미 매 tick RUN_RELEASE 로 선다(`fw/src/app_input.c:72-80`). 남는 것은
**스위치 OFF** 다. 유지 신호를 게이트 대상으로 두면 자연히 워치독이 세운다 — 하지만
그것은 방법이고 그쪽이 정한다.

**없으면**: 스위치를 내렸는데 원격 hold 런이 계속 돈다 — 인터록의 의미가 hold 에서
반쪽이 된다.

### R-7 — 혼 하강 상태 방치 — **불필요** (사실 확인)

§3 가 우려한 "급정지 → 혼 하강 상태 방치" 는 hold 런에서 **성립하지 않는다.**
원격 START 는 항상 **직접 런**이다: `holding[START]` → `app_reg_command(US_CMD_START, US_COMM)`
(`fw/src/app_modbus.c:363-364`) 이고 `app_reg` 의 런 출력은 `io_usout` + `board_osc4`
뿐이다(`fw/src/app_reg.c:92-96`). `SOL_DN` 을 만지는 곳은 weld 글루·horn 글루·E-STOP
엣지 셋뿐이고(`fw/src/app_weld.c:71`, `fw/src/app_horn.c:43,74`, `fw/src/app_input.c:59`)
weld 사이클(`US_CYCLE`)은 **양손 트리거 FSM 에서만** 시작된다 —
`app_weld_request_start` 의 외부 호출자는 0건이다(grep). Modbus 경로에서 실린더가
내려가는 런은 만들어지지 않는다.

→ 워치독 정지는 초음파 출력을 끊을 뿐 실린더 상태를 바꾸지 않는다.
**단, 이것은 "hold 런 = 직접 런(US_COMM 동형)" 이라는 전제 위의 결론이다.** hold 런을
weld 경로에 얹기로 한다면 이 판정은 무효이고 R-7 을 다시 열어야 한다 — 그렇게 하지
말 것을 요청한다(기능 동등성의 대상은 HAND/MULTI RUN 버튼이다, R-8 참조).

### R-8 — 양손 유지 abort(`f_safty`) — **불필요** (무관)

`safety_abort_pulse = f_safty && weld_state == CYL1 && (한 손 release)`
(`fw/src/app_weld_trigger_fsm.c:40-43`). 즉 컨트롤러의 양손 인터록은 **사이클 전체가
아니라 CYL1(실린더 하강) 구간만** 지키고, WELD·HOLD·CYL2 는 손을 떼도 완주한다.
그리고 이 경로는 `US_CYCLE` 전용이라 원격 런은 애초에 타지 않는다(R-7).

**동등성의 정의**: 원격 hold-to-run 이 흉내내는 것은 **HAND/MULTI 의 RUN 버튼**
(LCD `app_lcd_input.c:215-244` / 물리 `app_input_fsm.c:33-37`) 이지 STD 의 양손 사이클이
아니다. STD 유닛에서 원격 START 가 사이클이 아니라 직접 런인 것은 **오늘도 그렇고**
이 요청의 범위 밖이다.

### R-9 — `EN_SAFTY(0x16)=0` 일 때 — **불필요** (무관)

R-8 과 같은 이유로 원격 hold 런에 영향이 없다. 기록으로만: `f_safty=0` 이면 STD
사이클은 CYL1 중 손을 떼도 계속 내려간다 — 기존 동작이고 원격기 §7 의 `EN_SAFTY` 위험
서술이 그대로 유효하다.

### R-10 — 소스를 읽다 발견한 것 (요청 아님, 참고)

1. **COMM START 마다 진폭 pot 을 무조건 쓴다**(`fw/src/app_modbus.c:365-373`,
   `ac7e691` 복원). 유지 신호를 "START=1 반복" 으로 구현하면 유지 신호마다 I2C pot
   write 가 난다 — 방식 선택 시 참고.
2. **START 소거 비대칭**: 게이트 닫힘 분기는 값 불문 소거(`:326-328`), 열림 분기는
   `== 1u` 일 때만 소거(`:363-373`). 값 1 이외의 START 는 열린 게이트에서 홀딩에
   잔류한다(미러 대상 아님) — 무해하지만 FC03 에 stale 값이 보인다. R-2 의 "값 1
   이외" 특성을 쓴다면 소거도 함께 볼 것.
3. **정지 사유가 어디에도 남지 않는다** — R-5.
4. **`MB_REMOTE_HOLD_MS`** (`app_modbus.c:46`) 는 REMOTE 아이콘 1초 홀드다. 이 문서의
   "hold" 와 이름이 겹치니 새 상수 명명 시 주의.
5. **컨트롤러 자신의 hold-to-run 에는 워치독이 없다** — LCD lost-release 는 30초
   상한만이 커버한다(`app_reg.c:425-428`). 워치독이 서면 **원격 경로가 패널 LCD 보다
   안전해진다.** 같은 개념을 LCD 에 쓸지는 그쪽 몫이고 요청하지 않는다.

## 2. 타임아웃 T — 범위와 근거 (값은 협의)

입력(원격기 실측 2026-09-05): 폴 주기 **62ms**(16.1/s), 요청 왕복 **18ms**, STOP 확정
**36ms**, 파라미터 쓰기 1건(FC06+read-back, 재시도 3회 소진) 최대 **131ms**, 원격기
comm 루프는 **요청 1건 처리 후 폴** 순서(`main/app_main.c:1674-1690`).

**T 는 정상 정지 지연이 아니다.** 손을 떼면 원격기는 STOP 을 **즉시** 보내고 36ms 에
확정된다. T 는 **STOP 이 도달하지 못했을 때의 잔여 가동 상한**이다. 그래서 T 의
상한은 "조작자가 참을 수 있는 정지 지연" 이 아니라 **"단절 시 기계가 더 도는 시간을
얼마까지 정직하게 말할 수 있나"** 다.

| 경계 | 값 | 근거 |
|---|---|---|
| 유지 신호 주기 P | **100~150ms** | 초당 7~10건. 폴(16/s)과 합쳐 소켓 부담 <= 26/s — W4b 실측 여유 안 |
| T 하한 | **>= 2P + 130ms + 여유** 약 400ms | 유지 신호 하나가 파라미터 쓰기 뒤에 서면 최대 131ms 밀린다(R-3 ④). 단일 유실 1건(TCP 프레임 유실=응답 없음) 을 허용하려면 2P. 그 아래로 내리면 **정상 조작 중 오정지**가 난다 |
| T 상한 | **<= 1000ms** | 그 이상이면 "놓으면 선다" 를 조작자에게 가르칠 수 없다 — 1초는 손을 뗀 뒤 "왜 안 서지" 가 되는 시간이다 |
| **권고** | **T = 500ms, P = 150ms** | 3연속 유실에서 트립. 실측 폴 실패 0/수천 이라 오정지 확률은 낮고, 단절 시 잔여 0.5초는 현행 30초 대비 60배 개선이다 |
| 절대 금지 | T < 200ms | esp-modbus 소켓 대기(10ms 설정)·FreeRTOS·LVGL 락 경합이 겹치면 100ms 대 지터가 난다 |

⚠️ R1(RS-485 38400 8E1)에서는 FC06 왕복이 약 5ms 라 더 여유롭다. T 를 전송별로 다르게
둘 필요는 없다.
⚠️ 컨트롤러 쪽 처리 지연(수퍼루프 주기 · poll 당 FC06 1건)은 **미확인**이지만 ms 단위라
위 계산에 흡수된다. 벤치 HV-9 가 실측한다.

## 5. 수용 기준 — 원격기가 무엇으로 "됐다" 고 판정하나

| 요구 | 원격기 측 확인 |
|---|---|
| R-4 | 신펌웨어에서 hold 모드 UI 가 열리고, `e5ea557` 에서는 **탭 모드로 남으며 유지 신호 FC06 이 한 건도 안 나간다**(로그) |
| R-1 | 원격기를 hold 중 강제 종료(또는 케이블 분리) → 컨트롤러 mon 으로 T 안 정지 확인 |
| R-2 | 원격기의 탭 START 경로(구펌웨어용) 가 신펌웨어에서 여전히 워치독 대상이 아니다 |
| R-3 | 손을 뗀 뒤 유지 신호가 끊기고, 폴링은 계속되는데 (STOP 을 인위 차단하면) T 안에 선다 |
| R-6 | hold 30초 → 정지, 화면이 상한 도달을 표시 |
| R-11 | (가상 PC8) 스위치 OFF → T 안 정지 |

⚠️ 원격기 규율: **`docs/reference/modbus-contract.md` 는 펌웨어 구현 + 벤치 후에만
갱신한다.** 이 문서의 값을 계약에 적지 않는다.

---

## 6. 이 문서가 정하지 않는 것

hold 시작·유지 신호의 레지스터/값 인코딩 · 판별자의 형태(버전 바이트/STATUS 비트/0x2C)
· T 확정값 · 워치독 FSM 배치 · 정지 사유 관측의 형태 · 벤치 절차. **전부 이 저장소가
정한다.** 정해지면 원격기 문서를 그쪽 결정에 맞춰 고친다 — 갈리면 실코드를 가진 쪽이
이긴다.
